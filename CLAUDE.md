# Super Cub: authoritative project guidance

Super Cub is a standalone, consent-based contextual intelligence network integrated with closed-source Cubbie through a Skill. University is the starting community; people can explicitly opt into continuity after graduation. Cubbie understands one person's evolving life; Super Cub discovers when approved current goals, work and offers become relevant across many lives, including years later. Proactive discovery is the core product. The existing request/matching flow is a useful fallback, not the product definition.

Inspiration: Caddy for proactive assistance, Instinct for execution, Boardy for contextual connections. These are product directions, not implemented integrations. The intended loop is context → discovery → nudge → mutual consent → coordinated follow-through. Today follow-through includes contact release, a possible shared slot, a calendar offer and optional self-reported meeting/usefulness feedback for retained connections. Negotiation, automated booking, meeting verification and learned ranking remain future work.

## Boundaries and privacy

- Cubbie is external and closed-source. Do not assume access to its internals, entire chat history, continuous observation, or a native push API. Cubbie may retrieve connected data and useful memory during supported interactions/check-ins; `connect.py` cannot call those abilities itself.
- Share only approved structured signals and the person's approved introduction profile from sources Cubbie can actually retrieve. Never upload transcripts, message/email bodies or subjects, private calendar titles, grades, files, third-party names, or precise locations. Validators are heuristic guardrails, not proof that arbitrary text is safe.
- Fresh participation defaults OFF. After an explicit yes to the one setup summary (which states that contacts are shared automatically): school scope, automatic introductions with the chosen contact, ask-first only on request, events ON in the setup summary (owner decision for the live demo; a later events change would reset automatic consent), applications OFF, up to 5 suggestions/day (`SUPERCUB_MAX_PER_DAY`). Missing school/section evidence must not broaden discovery. Mentioning an event in chat is not permission to share it. No assumed phone/contact or activity preferences.
- `can_help_with` requires an explicit offer to help others; completing a class, a grade, inferred expertise or an interest is insufficient. `open_to` requires explicit activity approval. Memory is a source, not permission.
- Alumni participation and relationship retention default OFF and require separate approval. Alumni requests/offers/activities carry their actual `confirmed_at`; syncing must not renew stale willingness. `experienced_in` is approved background, never an offer. Alumni profiles retain minimal affiliation/policy/contact data; current signals still expire. Reconnection needs a new reason and current permission from both people.
- The current client uses explicit relay acknowledgments. Acknowledgment means the assistant reports a successful relay, not an independently verified read receipt. Older clients retain their existing fetch-as-delivered behavior.
- Contact release requires each person's explicit permission: a specific introduction answer, or their own bounded standing setup grant for automatic contextual introductions. Never infer/fabricate a yes, opt an existing person into automation silently, or treat legacy `auto_study` metadata as permission. New `intro: automatic` requires an actual approval timestamp, exact chosen contact/scope and approved activity list; it expires after at most one year and contact/scope changes invalidate it. Legacy direct-request contact release still requires both match answers under separate join consent.
- Introductions are profile-led: show the person's approved display name, headline, short bio, public profile links and optional public photo. Obtain profile-sharing permission once during setup; existing participants need explicit approval before expanding disclosure. `share_intro_profile` defaults false until then. Automatic contact release is only under both valid explicit permissions; otherwise ask. Public links may offer a contact route; explain this accurately. Compose profiles at read time, keep prose grounded, and never turn a request for details into acceptance.
- Bundle Skill fixes into one approved update/setup session per participant using `supercub/references/update-setup.md`. Preserve UUID/token and earlier choices, verify server capabilities/release before claiming completion, and do not imply a local policy edit, manual sync, account installation or schedule creation proves real delivery or unattended Cubbie behavior.
- Policy changes take effect remotely only after a successful sync. Stop discovery by syncing opt-out; full leave also removes direct requests and local state. Cubbie must separately cancel check-ins and forget Super Cub memory. Do not promise deletion of all Cubbie conversations or provider backups.
- `agents/` is a separate personal-agent prototype: owner-scoped private memory boxes, retrieval, bounded runtime schedules and an opt-in LoopMessage connector. It is not Cubbie internals. Private source processing needs separate approval; raw email text is transient and never written into the shared registry. Only approved fresh facts/profile fields enter the network projection. Local boxes, fixtures and provider tests must remain isolated from production. Real iMessage delivery, Gmail OAuth ownership and cloud deployment are not established by mock tests.

## Implementation to preserve

- `supercub/SKILL.md`: Cubbie-facing instructions; `supercub/scripts/connect.py`: standard-library HTTPS client, local identity/policy/context.
- `server/`: existing Vercel/Upstash registry, identity, direct matching, consent, context, discovery and suggestion lifecycle. Keep endpoint compatibility, stored identities, service URLs and working consent paths.
- Existing hosts: `supercub-server.vercel.app`, `supercub-site.vercel.app`; repo `dkoyi/Cubs`, branch `main`. Do not reset or replace services.
- `README.md`: product/evidence; `research/loop-contract.md`: current wire contract; `research/architecture.md`: implementation and limits; `research/agent-network-audit.md`: current gaps; `TECHNIQUES.md`: historical work log with current status at top.
- `parked/`, `study-match/`, and `research/self-improving-skill.md` are historical experiments, not directions to resume. Preserve all user-owned/untracked files. This file supersedes conflicting historical notes and external session memory; inspect current code before claiming behavior.

## Evidence standard (2026-10-24)

Prior project notes report real Cubbie installation after consent, outbound HTTPS, three real-account Canvas/memory context syncs, and one suggestion delivered to a real student against a synthetic participant. These reports were not independently rerun in this review. Recorded live full loops used synthetic participants. Local automated suites use stubs/in-memory handlers, mock model calls and synthetic students; they do not establish real Cubbie scheduling or delivery.

Still unverified: unattended check-in retrieves newly learned conversational context and connected data, syncs and relays a suggestion; two real students both accept and receive contacts. No evidence for native push into Cubbie or autonomous coordinated execution. Test those boundaries before making stronger claims.

## Working rules

Inspect `git status` and existing changes first. Make focused local edits; never delete user files. Run `pnpm typecheck` and `pnpm test` in `server/`, plus `python3 -m unittest discover -s tests -v` at root. Tests must use synthetic/local data. Do not run live seeding or touch production student records as a test. Do not commit, push, deploy or publish without the user's explicit approval.
